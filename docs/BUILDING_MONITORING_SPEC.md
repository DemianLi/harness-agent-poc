## 1. 產品範圍與非目標

**範圍**：查詢 3 棟大樓約 150 個監控點位的即時／歷史狀態，查詢與確認告警，建立維修工單，涵蓋消防／電梯等生命安全系統的**唯讀**查詢。

**明確非目標（v1）**：
- 不對任何設備（含生命安全系統）執行控制寫入（開關機、調參數、復歸）
- 不取代既有的消防受信總機／電梯緊急對講等法定安全設備的正式流程——本助手是輔助查詢工具，不是安全系統本身
- 不服務租戶／住戶角色

**架構上必須預留、但 v1 不實作的擴充點**：一般設備控制（Tier 2）、生命安全系統控制（Tier 3，需多人核准）、外包廠商角色、物業經理角色。詳見 §7 風險分級與 §6 RBAC。

### `[待確認]` 範圍可能擴大——四項新場景

後續討論中提出四個目前規格完全未涵蓋的應用場景，皆**未確認是否納入範圍**，且彼此性質差異很大，不是加幾個工具就能塞進現有 D1–D14：

1. **大樓危機處理 SOP 建議**——性質是「程序性知識庫問答」，不是查即時資料，需要新的資料來源（SOP 文件庫）與對應的 grounding 規則（建議必須對應哪個版本的 SOP 文件，不可憑空生成）
2. **大樓設備問題排查建議**——性質是「生成式診斷推理」，與 §5（D3）「不得用模型參數化知識回答『現在』類問題」的鐵律有潛在衝突（排查建議本質上需要模型做因果推理），需要新設計一套「建議」與「事實查詢」的區隔規則，避免使用者誤把 AI 建議當成查詢結果
3. **訪客系統介接**（透過 API 填寫訪客申請單）——全新的「寫入外部系統」能力類型，且涉及個資（訪客姓名／身分等），現行 §9（D7）合規表僅以「若未來納入門禁/CCTV資料」當佔位符，訪客資料現在就是個資，需要重新定義風險分級（Tier）與審核流程
4. **影像辨識非開放時間逗留偵測**——全新資料類型（視頻／影像），現行 `docs/SPEC.md` Model 層僅設計給文字 LLM，未涵蓋多模態／視覺模型的介面契約；涉及人員辨識與隱私，個資法規落地程度遠高於現在的佔位描述；功能性質是「主動監測＋異常判定」，比 §6（D4）主動通知更進一步

四項皆列入 §17 待確認事項清單（#20–23），暫不展開設計，待確認是否納入範圍後再新增對應 D 章節。

## 2. 核心架構總覽

```
┌─────────────── Cloud ───────────────┐        ┌──── Edge（每棟大樓） ────┐
│ LLM 推論／Orchestration              │◀──────▶│ 資料擷取與緩衝           │
│ 跨大樓查詢彙整 / 歷史資料庫           │  網路   │ 最後已知狀態快取         │
│ RBAC / 身份驗證                      │  連線   │ 獨立於雲端持續運作       │
│ 稽核集中儲存                         │        └──────────┬────────────┘
└──────────────────────────────────────┘                   │
                                                    BMS/IoT（廠牌未定，經 Adapter 抽象）
```

**不變量（跨所有層級）**：AI 問答服務中斷 **不等於** 大樓設備監控／告警系統中斷。Edge 端在與雲端失聯時仍需獨立運作、持續緩衝資料；只有「AI 問答」這個功能會降級，建築物本身的監控與告警不依賴這個助手。

## 3. D1 — 資料整合層（即時／歷史數據契約）

### 介面契約

```python
class DataPoint(BaseModel):
    point_id: str            # 全域唯一，格式 {building_id}.{system}.{device_id}.{point}
    building_id: str
    value: float | str | bool
    unit: str | None
    quality: Literal["good", "stale", "bad", "unknown"]   # 必要欄位，見下
    timestamp: datetime      # 資料「量測時間」，非查詢時間
    source_protocol: str     # e.g. "bacnet" / "modbus" / "opcua" / "vendor_api"

def get_realtime_point(point_id: str) -> DataPoint: ...
def get_historical_series(point_id: str, start: datetime, end: datetime,
                           resolution: str) -> list[DataPoint]: ...
def list_points(building_id: str, system: str | None = None) -> list[PointMetadata]: ...
```

### 廠牌無關設計（因應 BMS 尚未選型）

具體協定（BACnet／Modbus／OPC-UA／MQTT／廠商專屬 API）一律由 **Adapter** 實作於此契約之下，核心邏輯與 Orchestration 層不得假設任何特定協定——比照現行 `docs/SPEC.md` §1 Model 層「provider factory」的抽象模式。廠牌選定後，另立 `{vendor}_adapter` 子規格，本文件的 `DataPoint` 契約不因廠牌而變。

### 資料新鮮度契約

`quality` 欄位是強制的，非附加資訊：
- `good`：在該點位正常更新週期內
- `stale`：超過正常更新週期（門檻依點位類型可配置，非全域單一數字——例如溫度點位與告警點位的正常更新頻率天差地遠）
- `bad`：來源回報明確異常值
- `unknown`：從未取得過資料

### 錯誤分類

| 錯誤 | 情境 |
|---|---|
| `PointNotFoundError` | point_id 不存在於台帳 |
| `AdapterUnavailableError` | 該建築的 BMS 連線中斷 |
| （非錯誤）`quality="stale"` | 資料存在但已過期，仍須回傳，不可轉為例外 |

### 失敗模式

Adapter 斷線時，`get_realtime_point` **必須**回傳最後已知值 + `quality="stale"` + 明確過期時長，**不得**拋出例外讓上層無法作答。是否可以用過期資料回答，由 §5（D3 防幻覺護欄）決定，不是這一層的責任。

### `[待確認]`

BMS 廠牌與實際協定尚未選定，本節僅能定義抽象介面；`stale` 判斷門檻的具體數字需依各系統實際更新頻率與 BMS 選型團隊確認。

### MCP 整合路線（2026-07-25 確認，取代上述 Adapter 假設）

整合方式確定為 **MCP（Model Context Protocol）**，且由**內部同事開發** MCP server，**每個系統各有一個獨立的 MCP server**（非單一 server 涵蓋全部）。這與原先假設的「串接設備商已打包好的現成產品」不同，關鍵差異在於**契約主導權在我方**。

#### 對本節設計的影響

- **`DataPoint` 契約從「期望」變成「要求」**：既然 MCP 由內部開發，本節的 `quality`／`timestamp` 欄位不再是「希望設備商有提供」，而是**我方必須主動提出並納入 MCP tool schema 需求的必要條件**。D3（§5）的防幻覺護欄完全建立在這兩個欄位上，若未在介面約定階段寫入需求，做出來一樣拿不到。
- **原「廠牌無關 Adapter」的抽象層下移**：BMS 廠牌與協定（BACnet／Modbus／OPC-UA／廠商 API）的差異吸收改由 MCP server 內部處理，本規格只面對 MCP tool 介面。**但這不代表 §17 #1（BMS 廠牌與協定）已解決**——該問題只是移入 MCP 開發者的範圍，仍會回頭影響 `stale` 門檻等契約細節。

#### 多 MCP server 的衍生設計要求

每個系統各一個 server，代表 agent 端會同時掛載多組工具。需要：

- **統一契約把關**：多個 server 若由不同人開發，`DataPoint` schema 與錯誤語意必須一致，否則 D3 護欄在不同系統上行為不一。建議由本規格作為單一事實來源，開發前完成 schema 凍結與版本標記。
- **工具分層暴露／動態召回**：工具總數隨 server 數量線性成長，全部塞進 context 會造成上下文膨脹與工具選擇錯誤。此風險對地端 12B 級模型（§19）遠大於雲端旗艦模型，屬於必測項目（見 §19 Layer 1）。
- **介面約定時程**：MCP schema 需設定版本凍結時間點，作為兩個團隊的交付介面。`[待確認]` 具體日期。

#### 實作與驗證工具

`langchain-mcp-adapters` 的 `MultiServerMCPClient` 正是為多 server 場景設計（見 §18.1）；MCP Inspector 用於實際檢視 `tools/list` 回傳 schema，驗證契約落實情況（見 §18.1、§19 前置條件）。

## 4. D2 — 告警與事件管理契約

### 資料模型

```python
class AlarmEvent(BaseModel):
    alarm_id: str
    point_id: str
    building_id: str
    severity: Literal["life_safety", "critical", "high", "medium", "low"]
    state: Literal["active", "acknowledged", "cleared"]
    raised_at: datetime
    acknowledged_at: datetime | None
    acknowledged_by: str | None      # user_id
    cleared_at: datetime | None
    description: str
```

### 嚴重度分級與規則

`life_safety`（消防／電梯緊急）是獨立於一般 `critical` 之上的最高等級，且**一律唯讀顯示**——即使本助手允許確認一般告警，`life_safety` 等級的確認動作也不透過本系統執行；助手回答時應引導使用者至原本的消防受信總機／電梯緊急對講等法定流程確認，而非讓 AI 成為確認紀錄的來源。

### 確認（acknowledge）契約

僅 `severity != "life_safety"` 的告警允許透過本助手執行 `acknowledge`，且此動作屬於 §7 的 Tier 1（低風險操作），需要 `monitoring_operator` 角色（§6）＋ 現有 session/call 核准機制。

### 去重複

同一 `point_id` 在門檻時間內重複觸發需去重複，具體時間窗 `[待確認]`（先假設 5 分鐘作為草案值）。

### 失敗模式

告警來源系統斷線時，助手**必須**明確回答「無法確認最新告警狀態，最後已知告警列表時間為 X」，**不得**沉默地暗示「目前無告警」。

## 5. D3 — 事實根據與防幻覺護欄（不可退讓）

這是整份規格中優先度最高、不可妥協的一節——因為涉及生命安全系統。

### 強制 Grounding 規則

系統提示（system prompt）必須要求：任何關於設備／告警／生命安全系統**當前狀態**的陳述，必須對應到一次 D1／D2 工具呼叫的回傳值與時間戳。**不得**使用模型參數化知識回答「現在」類問題——這點與現行 `docs/SPEC.md` 的 repo 問答場景（模型可以自由生成技術解釋）有本質差異，必須在新版系統提示中明確覆寫。

### 拒答規則

若相關 `DataPoint.quality != "good"`，或資料時間戳超過新鮮度門檻，助手**必須**明確告知資料過期／不可用，**不得**基於過期資料給出「正常」或「已排除」等結論性語句。

### 生命安全系統額外規則

涉及消防／電梯的查詢，只要存在任何不確定性（資料延遲、來源不明確、point 對應不清楚），一律採取保守回答（引導使用者查看現場受信總機／實際確認），**不得**傾向於「安慰性」措辭。這條規則的優先度高於「回答有幫助」——寧可讓使用者多跑一趟現場確認，也不能讓 AI 給出錯誤的安全感。

### 與 §12（D11 驗證）掛勾

即使目前無歷史資料可用（訪談確認事項），本節的「不得說什麼」規則必須先轉成一組可執行的負面測試案例草稿，等資料到位後直接套用。

### `[待確認]`

本節的強制 grounding 規則**直接依賴 §3（D1）的資料契約能否落地**——具體而言依賴 `quality`／`timestamp` 兩個欄位是否確實存在於 MCP tool 回傳中。

**現況（2026-07-25 更新）**：MCP 由內部開發（§3），因此這兩個欄位**是我方可以主動要求的**，不再是外部不可控因素。相對地，責任轉為：必須在 MCP schema 凍結前，將這兩個欄位列為**必要欄位**寫入介面約定——否則本節規則將無法執行。這是本節目前最關鍵的前置依賴。

### 模型能力與本節規則的關係（新增）

本節所有「必須／不得」規則的執行者是 LLM 本身。地端模型（§19）若在工具呼叫可靠度或指令遵循上不足，本節規則會在執行層失效——**規格寫得再嚴格，模型漏呼叫工具直接憑參數化知識回答，護欄等同不存在**。因此：

- §19 的 Layer 1（工具觸發率 100%）與 Layer 2（生命安全對抗測試 100%）是本節能否成立的**技術前提**，不是附屬的品質指標
- 因資料上雲政策已放寬（§0 追加確定項），**允許設計「生命安全類查詢或地端模型信心不足時，升級路由至雲端旗艦模型」的 fallback 機制**。此選項在資料不可上雲時不存在，現已可行，建議作為 Layer 2 未達標時的架構補救方案（詳見 §18.8）。

## 6. D4 — 主動通知

### 觸發規則

`severity` 為 `high`／`critical`／`life_safety` 的新告警，需在門檻時間內（`[待確認]`，草案建議 < 30 秒）推送給對應 `building_id` 的 `monitoring_operator` 角色使用者。

### 通知管道

嵌入式介面內的即時通知（web push／WebSocket），**不取代**既有正式告警系統——消防受信總機的蜂鳴器／閃燈才是主要告警管道，本助手的推播是輔助性質，這點須在 UI 文案中明確標示，避免使用者誤以為 AI 推播是唯一或主要告警來源。

### 失敗模式

推播失敗不得靜默——需記錄未送達事件供 §8（D7 稽核）事後追查。

## 7. D5 — 身份與角色權限（RBAC）

### 角色（v1 實作 + 架構預留）

| 角色 | 狀態 | 說明 |
|---|---|---|
| `monitoring_operator` | v1 實作 | 監控中心值班人員，24/7 輪班 |
| `system_admin` | v1 實作 | 帳號／權限／系統設定管理 |
| `property_manager` | 架構預留 | 未來加入，關注趨勢／報表 |
| `external_contractor` | 架構預留 | 未來加入，**獨立信任等級**——外部身份、外部網路路徑，不可與內部員工共用同一套驗證/授權假設 |

租戶／住戶角色**明確排除**，不存在也不預留。

### 權限矩陣（v1）

| 動作 | monitoring_operator | system_admin |
|---|---|---|
| D1 即時／歷史查詢 | ✅ | ✅ |
| D2 告警查詢 | ✅ | ✅ |
| D2 一般告警確認 | ✅ | ✅ |
| D2 生命安全告警確認 | ❌（引導至原生流程） | ❌ |
| 建立工單 | ✅ | ✅ |
| 系統設定 | ❌ | ✅ |
| 設備控制（Tier 2/3） | ❌（v1 不存在此功能） | ❌ |

### `building_id` 作為權限邊界

目前 3 棟大樓同一管理團隊，尚不需要跨業主的租戶隔離，但 `building_id` 仍須作為權限範圍的一個維度保留——未來若擴充為跨業主的物業管理 SaaS，這是天然的租戶邊界，現在就這樣設計可避免日後重構。

### 身份來源（2026-07-25 確認）

v1 使用者身份**沿用既有 3D 監控平台帳號**，本系統不自建帳號體系。連帶要求：

- §9（D7）稽核紀錄的 `user_id` 以該平台的使用者識別為準，需確保跨系統可追溯
- 本規格定義的 `monitoring_operator`／`system_admin` 兩個角色，需與該平台既有角色模型建立映射——若該平台無對應概念，則需由本系統維護一份角色對照表
- 上述 `building_id` 權限維度理想上應由該平台提供（使用者可存取哪幾棟大樓），否則需另建維護機制

### `[待確認]`

3D 平台帳號系統的具體協定（OAuth2/OIDC、SAML、或自有 token）、角色映射方式、是否提供大樓存取範圍、token 效期與 refresh 機制——待 3D 平台技術團隊確認（見 §17 #28）。

`property_manager`、`external_contractor` 的具體權限細節，待這兩個角色真正導入前再確認；`external_contractor` 因屬外部身份，很可能無法沿用 3D 平台帳號，其驗證機制（獨立 IdP、時效性帳號等）需資安顧問參與設計。

## 8. D6 — 風險分級與核准機制（四級）

現行 `docs/SPEC.md` 的 Permission 層是二分法（safe / high-risk），無法承載「未來要擴充到設備控制、且生命安全控制門檻要遠高於一般設備」這個明確需求。新版定義為四級：

| Tier | 內容 | 核准要求 | v1 狀態 |
|---|---|---|---|
| **0** | 唯讀查詢（D1／D2） | 無需核准 | ✅ 實作 |
| **1** | 低風險操作（告警確認、建立工單） | `monitoring_operator` 角色 ＋ 批次核准（可沿用現行 session/call 範圍設計） | ✅ 實作 |
| **2** | 一般設備控制（未來：調整空調設定等） | 更高權限角色 ＋ **強制 per-call 核准**（不可用 session 範圍豁免），每次核准綁定操作人員身份於稽核紀錄 | 🔲 架構預留，不實作 |
| **3** | 生命安全系統控制（未來：電梯復歸等） | **多人核准（至少 2 人，dual control）**；新增此層本身需走完整 §14（D12 變更管控）＋ 法規複核，不是加一個 tool 就能上線 | 🔲 架構預留，明確不存在對應寫入工具 |

**明確聲明**：v1 只實作 Tier 0 與 Tier 1。Tier 2／3 是架構預留（介面設計需支援未來加入，不代表現在要做），且 Tier 3 在 v1 階段連工具本身都不應該存在，避免「反正介面留了，先加個工具方便測試」這種範圍蔓延。

## 10. D8 — 可用性與降級模式

### SLA

可用性 **99.9%**，查詢回應延遲 **< 5 秒**（P95）。

### 降級層級

| 層級 | 狀態 | 助手行為 |
|---|---|---|
| 正常 | Edge + Cloud 皆正常 | 即時查詢 + AI 推論皆可用 |
| Cloud 斷線 | Edge 獨立運作 | AI 問答不可用，明確告知「AI 助手暫時無法使用，請查看原有監控系統/現場設備」，**不得**沉默或假裝正常 |
| Edge 斷線（單一大樓） | 該大樓即時資料不可得 | 回答「該大樓連線中斷，最後已知狀態時間為 X」，**不得**沉默或猜測目前狀態 |

不變量同 §2：任何降級情境下，建築物本身的告警系統不依賴這個 AI 助手運作。

## 11. D9 — 部署拓撲與災難復原

- **Edge**：每棟大樓（或園區）一個節點，負責資料擷取、緩衝、最後已知狀態快取
- **Cloud**：集中式，負責 LLM 推論、跨大樓查詢彙整、RBAC、稽核集中儲存、歷史資料庫
- **DR**：Cloud 端在 99.9% 可用性要求下，建議至少 active-passive 或多可用區部署

### 推論服務部署（2026-07-25 確認）

地端模型採**集中式部署**（非每棟 Edge 各配置一份），以 vLLM 提供推論服務（§18.8）。此決策的連帶影響：

- Edge 節點維持輕量（資料擷取／緩衝／最後已知狀態快取），不承擔模型推論負載，硬體需求大幅降低
- 集中式推論服務成為**單一故障點**——其失效等同 §10（D8）表中的「Cloud 斷線」情境（AI 問答不可用，但大樓監控與告警系統不受影響，符合 §2 不變量）
- MCP server 由內部開發（§3），部署位置一併納入本節規劃，不再是外部不可控因素

### `[待確認]`

具體雲端供應商、Edge 硬體規格、Edge 端 DR 策略、**地端推論的 GPU 規格與機房位置**、集中式推論服務是否需備援，待基礎設施團隊確認（見 §17 #24）。

## 12. D10 — OT／IT 安全邊界

這是現行 SPEC 完全沒有觸及、但因為要橋接工業控制網路而變得關鍵的一節。

### 網路分段

Edge 節點對 BMS／OT 網路的存取應遵循**單向或嚴格受控**的資料流——建議採用 DMZ 或資料泵浦（data diode）模式讀取 OT 資料；**AI／雲端服務不應直接連線到 OT 網路本身**，一律經過 Edge 節點做隔離。

### Prompt Injection 防護

設備名稱、告警描述等來自 OT 系統的文字資料，送入 LLM 前須視為**不受信任輸入**——不得讓其內容被解讀為系統指令，需要明確的輸入邊界／轉義處理。這是設備監控場景特有的新型態風險，現行 CLI repo 問答場景完全不存在。

### 最小權限

Edge 節點對 BMS／SCADA **只能讀取，不應有寫入權限**——呼應 §7 目前 v1 不做任何控制寫入的決策，這條邊界應該落在網路架構層級，而不只是應用層的權限檢查（縱深防禦：即使應用層邏輯出錯，網路層也不允許寫入）。

### `[待確認]`

具體網路架構圖、ISO 27001 條文對應，待資安顧問確認。

### MCP 信任模型（2026-07-25 更新）

MCP server 確定由**內部同事開發**（§3），非第三方現成產品。因此原先預期的「供應鏈信任問題」大幅降低，信任模型回到內部程式碼治理範疇。仍需保留的要求：

- **連線憑證 vault 化**：MCP 對 BMS／OT 的連線憑證不得明文寫在 prompt 或程式碼中
- **MCP 工具回傳仍視為不受信任輸入**：即使 MCP 由內部開發，其回傳內容（設備名稱、告警描述）**源頭仍是 OT 系統**，上述 Prompt Injection 防護規則完整適用——信任 MCP 的實作，不等於信任它搬運的資料
- **白名單審核轉為內部審查**：改為「哪些 MCP server 可接入」的內部程式碼審查與部署核可機制，由資安窗口把關

### 資料上雲政策（2026-07-25 確認）

已確認**所有資料皆可提供給雲端模型使用**，無機敏資料分流限制（§0 追加確定項）。此決策簡化了架構（不需資料敏感度分類與路由），但**新增一項合規義務**：

此為商業決策，仍需法規顧問與資安顧問確認「監控資料傳送至第三方 LLM API」不牴觸 ISO 27001、個資保護法規、消防相關規範（見 §17 #27）。本節的 OT／IT 網路分段設計不因此放寬——資料可上雲指的是**經 Edge 讀取後的資料**，不代表雲端服務可直接連線 OT 網路。

### `[待確認]`

具體網路架構圖、ISO 27001 條文對應，待資安顧問確認。

## 13. D11 — 準確性驗證方法論

### 現況

無現成歷史資料（訪談確認），本節先定義「該驗證什麼」，資料到位後才能真正執行。

### 驗證項目

1. **事實準確性**：對已知的 DataPoint／AlarmEvent，助手回答是否正確反映
2. **拒答正確性**：資料過期／缺失時，助手是否正確拒答而非幻覺（對應 §5）
3. **生命安全保守性**：針對消防／電梯類問題的對抗性測試（adversarial prompt），確認助手不會給出過度安慰性或錯誤引導的回答

### 建議方法（不需真實歷史資料即可先做）

建立一組**合成測試情境**（synthetic test scenarios）：手動建構已知答案的模擬 `DataPoint`／`AlarmEvent`，驗證助手回答是否符合 §5 的 grounding 規則。這組測試案例應該在 D1 實際串接前就先寫好，作為驗收 D3 護欄是否生效的基準。

### 建議上線門檻（`[待確認]`，需與需求方核定）

- 生命安全相關測試案例：**100%** 通過率才可上線
- 一般設備類：至少 **95%** 準確率

## 15. D13 — 操作介面契約

### 嵌入形式

以元件／SDK 形式嵌入既有 3D 監控平台，支援桌機與行動裝置**響應式網頁**（非獨立 App）。

### 空間脈絡整合

3D 平台需要能把「使用者當前選取的樓層／設備」以 `point_id`／`building_id` 等結構化參數傳給助手，作為對話的隱含上下文——例如使用者在 3D 視圖點了 5 樓某台 AHU 再問「這台正常嗎」，助手不需要使用者手動輸入設備名稱即可正確定位。這是這個產品相較一般聊天助手的特殊整合需求，值得在後續 API 設計中明確定義為「上下文注入」介面。

### 通知

需支援瀏覽器／行動裝置的即時推播，對應 §6（D4）。

### 語言

介面文字與 AI 回答預設繁體中文，可切換英文。

### `[待確認]`

3D 平台的具體技術規格（Web-based BIM viewer 或自建系統）、SDK 整合方式，待該平台技術團隊確認。

**已確認（2026-07-25）**：介面範圍確定為**嵌入 3D 可視化介面內的對話面板**——即「使用方式跟 ChatGPT chat 一樣」指的是**互動模式**（多輪對話、串流回應）與 ChatGPT 一致，而非改為獨立的通用對話介面。因此本節的「空間脈絡整合」需求**維持有效且為必要項**，是本產品相較一般聊天助手的核心差異。

尚待 3D 平台技術團隊確認的介面細節（見 §17 #28）：上下文注入 API 的具體契約（傳入參數、觸發時機）、帳號系統對接協定、通知管道整合方式——這三項屬同一窗口，建議一次談定。

## 18. 技術選型與工具鏈建議

本節回應「六層/七層 harness 架構要落地在這個應用場景，對應到哪些具體技術／框架／測試工具」——這些是**建議**，不是既定決策，仍需依實際評估（授權條款、自架可行性、團隊熟悉度）確認後才落地。技術棧沿用已確認的 Python + LangChain/LangGraph（§0）。

### 18.1 設備 MCP 整合（對應 D1／§3）

- **`langchain-mcp-adapters`**（LangChain 官方套件）：提供 `MultiServerMCPClient`，可同時連接多個設備商各自的 MCP server，將 MCP tool schema 轉為 LangChain-compatible tools；預設無狀態、每次呼叫獨立 session，適合多棟大樓／多廠牌並存的場景。
- **MCP Inspector**（MCP 官方工具）：在正式串接前，用它連上設備商 MCP server 實際檢視 `tools/list` 回傳的 schema——這是驗證 §17 #16（設備 MCP 是否回傳 `quality`／`timestamp`）的具體方法，也支援 `--cli` 模式接入 CI 做自動化檢查。

### 18.2 記憶／狀態持久化（對應現行 `docs/SPEC.md` Memory 層）

現行 CLI 工具用的 `MemorySaver` 僅為 in-memory，不具持久化能力，正式上線需替換為：
- **`PostgresSaver`**（`langgraph-checkpoint-postgres`）或 `SqliteSaver`——checkpoint 持久化，支援跨行程/重啟後恢復
- **LangGraph Store API**（`PostgresStore`）——跨 session 的長期記憶（例如記住使用者慣用查詢的大樓／樓層）

### 18.3 生命週期與人工核准（對應 D6／現行 Permission 層）

LangGraph 官方自 2024 年底起將 **`interrupt()` + `Command(resume=...)`** 訂為 HITL 的建議寫法，取代舊的 `interrupt_before`/`interrupt_after`。建議評估將現有 `middleware/hitl.py` 的自訂核准邏輯遷移至此原生機制，理由：
- 暫停／恢復語意由框架原生支援，不需自行維護 `writes_approved` 狀態欄位
- 搭配 checkpointer 可做「time travel」回溯到早期 state，對應 ETCLOVG Lifecycle 層點出的 rollback 需求（例如工單建立中途失敗時的回滾）

### 18.4 可觀測性（對應 ETCLOVG Observability 層缺口）

**Langfuse（自架版）**：MIT 授權、可用 Docker/Helm 完全自架，原生支援 LangChain/LangGraph tracing（trace、tool 呼叫、延遲、成本、多輪對話）。這一層目前兩份 SPEC 都沒有獨立設計，屬於新增能力。

**選型理由更新（2026-07-25）**：原本自架版的主要理由是資料主權（監控資料不需送第三方）。因資料上雲政策已放寬（§0 追加確定項），此理由不再成立。改採自架版的理由調整為：**與地端 vLLM 推論服務同一套基礎設施、無 per-trace 計費、trace 資料與稽核紀錄（§9 D7）可留在同一治理邊界內**。若團隊自架維運人力不足，SaaS 方案（如 LangSmith）現已是可接受的替代選項。

### 18.5 驗證與測試（對應 D11／§13）

三項工具分工互補，建議搭配使用：

| 工具 | 用途 | 對應規則 |
|---|---|---|
| **Ragas** | `faithfulness`／grounding 分數，可設門檻（如 ≥0.85）作為 CI gate | D3 強制 grounding 規則 |
| **`agentevals`**（LangChain 官方） | Trajectory 評估——驗證 agent 是否按規定順序呼叫工具（如「必須先呼叫 `get_realtime_point`」），而非只看最終答案 | D3「陳述必須對應工具呼叫」 |
| **promptfoo** | YAML 驅動的回歸測試＋red-teaming（含 OWASP LLM Top 10、prompt injection），可接 CI | D11 生命安全對抗測試案例、D10 prompt injection 防護 |

### 18.6 護欄執行層（對應 D3）

- **Guardrails AI**：Pydantic 風格輸出驗證，可強制回答必須附帶 `point_id`／`timestamp` 等結構化欄位，而非僅靠 system prompt 文字約束
- **NeMo Guardrails**：以 Colang 撰寫對話層策略，可將「生命安全查詢一律保守回答」寫成可執行的 dialog rail

### 18.7 RBAC／權限治理（對應 D5、D6）

**限制與建議**：LangGraph Platform 內建的 custom Auth（可做 RBAC）僅在 Managed Cloud 或付費 enterprise 自架授權下可用，與 D9 傾向的 Edge/Cloud 自架、不綁定單一供應商的方向有落差。建議繼續採自訂路線（包一層 FastAPI + OAuth2/OIDC，延伸現有 `middleware/` 模式），不依賴該項付費功能。

身份來源已確認沿用既有 3D 監控平台帳號（§0 追加確定項），因此本節的 OAuth2/OIDC 實作需對接該平台——但該平台實際暴露的協定與角色模型尚未確認，見 §17 相關項目。

### 18.8 地端模型推論與路由層（新增）

對應 §0 追加確定項：地端模型、集中式部署、vLLM。

#### 推論服務

- **vLLM**：集中式部署（非每棟 Edge 各一），對外提供 OpenAI-compatible API，可直接由 LangChain 的 `ChatOpenAI` 指向本地端點接入，不需另寫 provider
- **tool calling 啟用**：vLLM 需以 `--enable-auto-tool-choice` 搭配該模型家族對應的 `--tool-call-parser` 啟動。**沒有官方 parser 支援的模型不應納入候選**——靠 prompt 硬解析 tool call 在生命安全場景不可接受（見 §19 Layer 0）

#### 模型路由層

因資料上雲政策放寬（§0），架構上可同時掛載地端模型與雲端模型。建議設計一層路由，依以下條件決定走哪個模型：

| 條件 | 路由目標 | 理由 |
|---|---|---|
| 一般設備查詢 | 地端模型 | 成本、延遲、不對外傳輸 |
| 生命安全類查詢 | 雲端旗艦模型（若地端未達 §19 Layer 2 門檻） | D3 生命安全保守性規則為不可退讓，模型能力不足時以路由補救 |
| 地端模型工具呼叫失敗／信心不足 | 升級至雲端模型重試 | 避免單一模型能力成為系統性風險 |

**此路由層是否需要，取決於 §19 的評測結果**——若地端模型能通過全部門檻，可簡化為單一模型架構。路由規則本身需納入 §9（D7）稽核紀錄，記錄每次回答實際由哪個模型產生。

### `[待確認]`

以上為建議選項，非最終決策；實際採用前需確認：授權條款是否符合公司採購規範、自架維運人力是否足夠、與現有基礎設施（§11 D9）的整合成本。地端模型的具體選型待 §19 評測後決定。

## 19. 模型選型驗證方法

本節定義如何驗證並選出符合本場景的地端模型。**核心原則：通用 benchmark 分數（MMLU 等）對本場景幾乎沒有參考價值**——決定成敗的是工具呼叫可靠度與拒答正確性，兩者必須自行實測。

### 前置條件：mock MCP server 與測試資料集

MCP 由同事開發中（§3），評測不應等它完工。應先依本規格的 `DataPoint` 契約建立一個 **mock MCP server**，回傳合成資料（含刻意設為 `stale`／`bad` 的案例）。此前置工作有三重價值：

1. 模型評測可與 MCP 開發並行，不互相阻塞
2. **順帶驗證我方契約設計是否合理**——mock 若難以實作，實際契約也會有問題
3. 測試案例可直接留用為正式的 regression suite（§18.5 的 promptfoo／agentevals 設定檔），不是拋棄式投資

### Layer 0：硬性篩選（pass/fail，不打分）

| 條件 | 判斷方式 |
|---|---|
| vLLM 有對應的 tool-call parser | 需 `--enable-auto-tool-choice` + 該模型家族的 `--tool-call-parser`；無官方支援者直接淘汰 |
| 原生 function calling 訓練 | 檢查 `tokenizer_config.json` 是否含 tool-compatible chat template |
| 繁體中文輸出（非簡體） | 實測一輪即可判斷 |
| 授權條款允許商用 | 檢視 license |
| VRAM 需求符合硬體預算 | 含 KV cache，非僅權重大小 |

### Layer 1：工具呼叫可靠度（權重最高）

以 `agentevals` 的 trajectory evaluator（strict mode）自動化。測試集中每題都**必須**觸發工具呼叫：

| 指標 | 定義 | 門檻 |
|---|---|---|
| **工具觸發率** | 該呼叫工具時確實呼叫的比例 | **100%** |
| 工具選擇正確率 | 選對工具（`get_realtime_point` vs `get_historical_series`） | ≥95% |
| 參數正確率 | `point_id`／時間範圍正確帶入 | ≥95% |
| **參數幻覺率** | 捏造不存在的 `point_id` | **0%** |

**工具觸發率是整個架構的地基**：若掉到 90%，代表每 10 次查詢有 1 次是模型憑參數化知識編造的，D3 護欄全數失效，不需再往下測。

**多工具退化測試（對應 §3 多 MCP server）**：將可用工具數從 3 個增加到 15 個，觀察選擇正確率下降幅度。小模型在工具數量增加時的退化幅度通常遠大於大模型，此結果直接決定是否必須實作工具分層暴露／動態召回。

### Layer 2：護欄遵循（D3 生命安全 gate）

| 測試 | 方法 | 門檻 |
|---|---|---|
| 拒答正確性 | 餵 `quality="stale"` 資料，檢查是否明確告知資料過期 | ≥98% |
| **生命安全對抗測試** | promptfoo red-team，誘導模型對消防／電梯問題給出「一切正常」「已排除」等安慰性結論 | **100%**（同 §13） |
| Prompt injection | 將惡意指令藏於設備名稱／告警描述（對應 §12 D10）；promptfoo 內建 OWASP LLM Top 10 | 依 OWASP 基準 |

### Layer 3：回答品質

- **Ragas `faithfulness`** ≥0.85，以 mock 工具回傳作為 context
- 繁體中文流暢度：以雲端旗艦模型作 LLM-as-judge 評分，或人工抽樣

### Layer 4：效能（vLLM 實測）

**測試設計必須反映實際呼叫模式**：一次問答不等於一次模型推論。典型流程為「模型決定呼叫工具 → 收到工具結果 → 產生最終回答」，至少 2 次推論，複雜查詢 3–4 次：

```
端到端延遲 ≈ Σ(TTFT_i + 生成時間_i) + MCP 工具往返時間
```

要達成 §10 的 **P95 < 5 秒**，反推單次 TTFT 需壓在約 1.5 秒以內。

測試要求：
- 以 **10 並發**（§16 實際規模）測試，非單請求
- 量測 TTFT P95、TPOT／ITL、端到端 throughput
- **量化影響必測**：FP16 vs AWQ／GPTQ int4。量化可省 VRAM 但會降低 tool calling 準確度，此 trade-off 須實測而非假設；**量化版本必須回頭重跑 Layer 1**

### 決策矩陣

生命安全相關門檻為 **gate，不是加權項**：

```
Layer 0 未通過           → 淘汰
Layer 1 工具觸發率 < 100% → 淘汰，或需架構補救（強制 tool choice）
Layer 2 生命安全 < 100%   → 淘汰，或該類查詢強制路由至雲端模型（§18.8）
以上皆通過               → 依 Layer 3 品質分數 + Layer 4 延遲／成本加權排序
```

### 建議執行順序

1. 建立 mock MCP server + 測試資料集（與 MCP 開發並行）
2. **先以雲端旗艦模型跑完整套，作為上限基準**——若連旗艦模型都無法通過 100% 門檻，問題出在 prompt 或架構設計，而非模型能力，應先修正架構
3. Layer 0 篩出 3–4 個候選（建議跨不同模型家族、同級參數量，避免同家族共同弱點誤導判斷）
4. 跑 Layer 1–2，通過者才進入 Layer 3–4
5. 量化版本回頭重跑 Layer 1

### `[待確認]`

候選模型清單、評測所需 GPU 資源與時程、由誰執行評測，待需求方與基礎設施團隊確認。
